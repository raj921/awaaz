Modal Training Pipeline Glossary

Every term anchors to your actual code: research/training/train_qwen3_sft.py (T) and serve_qwen3.py (S). Reviewed before interviews.

Modal — the cloud side

Modal App

The blueprint: a named bundle of functions declared in one file. Defining it costs nothing; it only runs when invoked. T:17

Container image

The recipe (OS + pip installs) a container is cooked from. Built once, cached; rebuilds only when dependencies change. T:18

@app.function

Marks a function for remote execution with hardware attached — gpu="H100" here. The function body runs only inside a container. T:92

.remote()

The teleport call: runs the decorated function in Modal's cloud, blocks your terminal until it returns, streams its prints back. T: local_entrypoint

@app.local_entrypoint

The part that executes on your Mac — modal run starts here. It just orchestrates: call each heavy function with .remote().

Volume

Cloud disk that outlives containers. The adapter written by training is read later by serving — different containers, same disk. T:25, S:19

volume.commit()

Flushes writes to the Volume. Skip it and the container's changes die with the container. T:126-129

download_base()

CPU-only function that snapshots the 3.4 GB base model to the Volume once — GPU containers then load from disk and never burn billed time downloading. T:77-82

add_local_file

Adds one local file (the MaSaC dataset) to the container's filesystem — mounted at startup, no image rebuild needed. T:18-21

modal run vs modal deploy

run = execute once, watch logs, container dies after. deploy = leave a standing endpoint alive for requests (serving). S: app "qwen3-a1-serve"

scaledown_window=600

Keeps the serving container warm 10 minutes after each request — the cold-start (minutes) never hits the latency budget. S:47

@modal.fastapi_endpoint(method="POST")

Turns the function into an HTTPS URL that accepts POST JSON and returns JSON. S:48

PEFT — the fine-tuning side

LoRA

Freeze the model; train tiny low-rank matrices beside attention projections. Adapter ≈ tens of MB instead of 3.4 GB.

DoRA

LoRA + separate magnitude/direction decomposition — near full-fine-tune accuracy, zero added inference cost after merge. Enabled with one flag. T:112 (use_dora=True)

LoraConfig(r=16, lora_alpha=32)

Rank 16 = adapter capacity; alpha ≈ 2×r is the conventional scaling. Targets: q/k/v/o attention projections. T:108-111

get_peft_model / PeftModel.from_pretrained

Wraps base + config for training / reloads a saved adapter onto the base for inference. T:108, S:38

Served unmerged (real lesson)

DoRA adapters merged into bf16 weights produced corrupted output (one garbage token for every prompt) — the adapter is served live instead. Cost: ~20 ms extra; truth: the model actually works. S:38

Prompt masking (-100)

Loss is computed only on the assistant's tokens; prompt tokens are labelled -100 (ignored). Labels are the pure content + <|im_end|> — the raw chat template would pollute them with think-wrappers the model then dutifully repeats. T:63

Serving — the latency side

server_ms / first-token latency

Wall time of generating exactly ONE token, measured inside the container with time.perf_counter(). Budget: < 200 ms warm. S:58-64

Why server-side

Your India→US round-trip (200-300 ms) would pollute a client-side number; the budget measures the serving infra, not geography.

Warm vs cold

Cold = container boots + weights load (minutes). Warm = model resident in GPU memory (milliseconds). Budgets apply to warm only.

vLLM (upgrade path)

Production serving engine — multi-LoRA hot-swap, continuous batching. Raw transformers.generate proves the budget; vLLM earns the throughput.
